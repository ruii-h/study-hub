PROCESS WORKFLOW MODEL (design Q) · draw checklist

  • Lane = who PERFORMS the activity (role, department or system), not the tool touched. A participant gets a lane only if it performs ≥1 activity. A change of lane = hand-off.
  • Activity types: Manual (human, no system) → human lane · Interactive (human uses a system) → HUMAN lane, system attached by a dotted association · Automated (system only) → system lane.
  • Events: circles. Start = trigger (e.g. customer walk-in). Every path must reach an end event; one end event per distinct outcome (rejected / approved / paid).
  • Activity = rounded rectangle, short verb–noun, one per step of the scenario; keep the scenario's order.
  • XOR gateway = diamond with ✖: one flow in, several out. Label EVERY exit (Yes/No, Approved/Rejected) and add % if given (75/25, then 90/10). Merge = several in, one out. AND = diamond with + (parallel). Count flows to tell decision from merge.
  • Solid arrow = sequence flow. Dotted line = association to a system / document name. Sub-process = + box. Timer = clock. Loop = arrow back.
  • Annotate when given: execution time (min), probability on branches, systems used, work products (or say you left them out).
  • State assumptions (email = hand-off channel, not a system/lane; work products omitted; separate process only triggered; which branch is the default).
  • Walk-through: read the scenario once and underline each actor, each system, each "if". Draw lanes first, then steps, then gateways, then ends.

RCI MODEL (design Q) · root cause, NO impact level

Columns: Issue # · Issue Description · Cause Description · Root Cause · Issue Category · Business Performance Metrics (+ Impact Level: not needed). Template may swap a column (e.g. Stakeholder).

  • Issue = the effect, written “X happens, which leads to Y”. Cause = why. Root cause = the deeper/common cause (5-Why or fishbone). Never restate the issue as its root cause.
  • One issue can have several causes → several rows, each with its own root cause and category.
  • Issue categories (5): Process (manual steps, redundancy, paper, wrong order) · System (slow/missing functionality, no automation in a system) · People (skills, workload, training, resistance) · Policy (rules, approvals, access rights) · Others.
  • Typical root causes: lack of automation (Process) · paper-based process (Process) · lack of system functionality (System) · department/company policy (Policy) · late exception check (Process).
  • Metrics: total process time, waiting time, cost per case, cost of rejection, # errors, # complaints, # missing forms, % on-time.
  • Example: AO emails each request → slow = lack of automation / Process; BAS slow, hard to search = lack of system functionality / System; AO cannot use the BAS = department policy / Policy.

RCR (next step): Root Cause → Recommendation → Impact score 5 = Very High … 1 = Very Low → Complexity 5 = Very Easy … 1 = Very Complex (higher = better on both). Do high-impact + easy first. Sources: domain, technology, best practice, experience.

BUSINESS & IT ALIGNMENT (SAQ)

  • Misalignment symptoms (5 questions): goals driving technology decisions? · IT enables business innovation? · shared accountability? · effective communication between teams? · technology strategy integrated with business strategy?
  • Root causes: IT does not appreciate business processes · business does not appreciate IT value · no common language · growing business / changing environment.
  • Steps: treat IT as transformative, not a cost centre · target customers internally and externally · IT and business “talk” in a common language · clear goals for IT · demand measurable ROI · write IT + business strategy in one document.
  • Enterprise alignment = whole organisation, via Enterprise Architecture. Project alignment = one IT solution, via Business Process Engineering Methodology.
  • Carr “IT doesn’t matter”: IT alone becomes a commodity; advantage comes from combining IT with strategy, processes and capability.
  • Four dimensions: Purpose = Why (mission, vision, goals) · Participants = Who · Process = How · Product = What. (“Project” is not a 4th P.)
  • BPM cycle: Discover → Model & Analyse → Design solution → Implement → Monitor & Optimise (never ends). Course: Model → Analyse → Solve → Innovate.

USE CASE DIAGRAM (design Q)

  • Actor = generic role noun (Patient, not “Max”); stick figure; can be a human, a device or an external system. Use case = verb–noun oval (Book Appointment). Association = solid line actor–use case. System boundary = rectangle, one per system.
  • Derive from the To-Be workflow:
ActivityBecomes
ManualNo use case
Interactive1 use case, linked to the human who does it
Automated, 1 system1 use case of that system (actor = who is served/notified)
Automated, 2 systems2 use cases: sender (client) in its boundary and receiver (server) in the other; each system is the actor of the other’s
  • Do NOT combine automated use cases (email + SMS = 2). Add extras: CRUD “view”, login, search.
  • Systems used but without a lane (annotated) are still actors. Notified person (e.g. LM) = actor.
  • Packages: group related use cases of one system, name by function; never across systems.

C4 CONTEXT DIAGRAM (design Q: “only draw the context diagram”)

  • Your system = one box (software system in scope). Around it: People (human actors/roles) and external systems you do not own (IMS, Gov website, Outlook, Bank).
  • Label every arrow with what flows (use case / data / protocol, e.g. “Sends notifications [email]”, HTTPS/RESTful API) and direction.
  • Two systems: draw both as boxes, give each its own users, join them with a labelled integration arrow (client → server).
  • No internals: no databases, applications, components. No Docker/containers here. Audience: everybody.
  • Map from Solve: human use-case actor → Person · system you build → system in scope · systems you don’t own → external system · integration use cases → labelled arrow. Add a short key.

DYNAMIC ANALYSIS · 8 TECHNIQUES (match the keyword!)

TechniqueUse when / keyword · example
1 CapacityMaximum the process or resource can handle (supply) vs demand. “200 orders/day but can only make 100”; “2 counters register max 96/h”.
2 Process cycle time/costTime and cost of the whole workflow per instance/customer: “each customer takes 15 min on average, $x”.
3 Resource utilisationIs a resource over- or under-used? Utilisation = workload ÷ capacity. >100% overloaded (127%); very low = idle → lower hours or reassign. Target e.g. 70–85%.
4 Activities time/costDuration and cost of each activity (mean, s.d.).
5 BottleneckProcess + resource + activity combined: long waiting time, long queue length, over-utilised resource. Not “the longest task”.
6 Path analysisPaths come from decision points. Check rejection cases; vary the probability (1–100%) and watch the path. Rank by expected contribution = share × cost (or time), not by frequency or per-case cost.
7 Unusual eventRare, high-impact events (flood, outage, strike).
8 What-ifChange one thing at a time (cashiers 2 → 3: cycle time 20 → 10 min). Find the smallest option that meets the goal, then check cost; lowest waiting time is not automatically best.
  • 4 phases: 1 Establish performance goals → 2 Model & simulate (As-Is, then each To-Be) → 3 Impact analysis (who is affected: hard/soft × internal/external) → 4 Final selection (goals + simulation + impact + management).
  • Simulation data: process-wide = arrivals, frequency, opening hours · activity = task time, cost, resource, queue rule · resource = cost/h, headcount, work hours, max utilisation · decision points = branch probabilities.
  • Random inputs → runs differ → run many times. Matching one average is not enough to call a model valid. Utilisation <100% does not rule out queues. Static report cannot show waiting.

STATIC REPORT FORMULAS

Input factor f = probability a task runs; nested branches multiply (80% × 60% = 48%).

Cycle timeCT = Σ t·f (min)
Cost / instanceΣ (t·f ÷ 60) × cost per hour of the role
Annual workloadW = Σ (t·f ÷ 60) × instances per year
Required resourcesR = W ÷ annual hours per resource
UtilisationU = R ÷ number available (>100% = overloaded)
Path contributionshare × value; Σ = weighted average
% improvement(As-Is − To-Be) ÷ As-Is × 100

Which activity contributes most to cycle time? Compare t·f, not t alone (18 min × 10% = 1.8 < 6 min × 100% = 6).

SOLVE · FUNCTIONAL vs NON-FUNCTIONAL

Functional = what the system does (features, data handling, user interaction) → drives use cases. Non-functional = how well / how it should be (performance “loads in 2 s”, security, usability, reliability “99.9% uptime”).

Solve method: Use case model → Use case packages → Function model → Architecture (C4) → Risk model → Cost model.

M12 · PROCESS ARCHITECTURE & VALUE CHAINS (MCQ only)

  • Core (value chain/primary): critical expertise, output goes to external customers · Supporting: outputs are inputs to core · Management: direction, rules, plans, controls (“regulations”).
  • Porter primary: inbound logistics · operations · outbound logistics · marketing & sales · service. Support: firm infrastructure, HRM, technology development, procurement. Value = total revenue buyers will pay. Organisations have ~3–15 value chains.
  • Process Executive Model: functional units = columns, processes = rows, levels 1–3, stops at level 3; a bar spanning columns = several units involved. Process Hierarchy Model: tree under one level-3 process, goes beyond level 3.
  • Frameworks: eTOM telecom · SCOR supply chain · APQC PCF cross-industry. Notations: Porter value chain, SAP Business Map. Faculty management = core, faculty services = support.

MCQ TRAPS · QUICK CHECK

  • Interactive activity = human’s lane. Manual = no use case. Business rules ≠ gateway. Complexity 5 = Very Easy.
  • Bottleneck ≠ longest task; path priority ≠ most frequent path. Cost model ≠ dollars. Container ≠ Docker. Context diagram = no internals.
  • Static = no execution (cheap, no waiting/queues); dynamic = simulation. Impact analysis = who is affected, not speed/cost.
  • Roles/reporting → Organisation; geography → Location; sequence → Workflow; IF-THEN → Business rules.
